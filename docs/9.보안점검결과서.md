### [점검 #1] OWASP A03 - 문서 검색 SQL Injection (SQLi) 점검

#### 1. 점검 개요
문서함 검색창의 검색어(`keyword`) 파라미터에 SQL 구문을 주입하여 비인가 문서 열람 및 DB 오류 유발을 시도함.

#### 2. 공격 요청 (Payload)
```http
GET /api/documents?keyword=%27%20OR%20%271%27=%271%27%20-- HTTP/1.1
Host: localhost:8080
Authorization: Bearer <사원_JWT_토큰>
```
* **입력값**: `' OR '1'='1' --`

#### 3. 서버 실제 응답 (Response)
```http
HTTP/1.1 200 OK
Content-Type: application/json;charset=UTF-8

{
  "success": true,
  "data": {
    "documents": [],
    "totalCount": 0
  },
  "error": null
}
```

#### 4. 방어 분석 및 판정
- **결과**: **방어 성공 (PASS)**
- **원인 분석**: JPA/Hibernate의 Named Parameter 바인딩(`WHERE d.title LIKE CONCAT('%', :keyword, '%')`)이 적용되어 있어 주입된 `' OR '1'='1' --`가 실행 구문이 아닌 단순 문자열 검색어로 안전하게 치환됨. SQL 문법 에러 및 데이터 유출 없음 확인.

### [점검 #2] OWASP A07 - 무차별 대입 공격(Brute-Force) 및 계정 잠금 점검

#### 1. 점검 개요
사원 계정(`sales.staff@baton.local`)에 대해 무차별 대입 스크립트를 통해 연속 5회 이상 잘못된 비밀번호를 전송하여 계정 잠금 정책 동작을 검증함.

#### 2. 공격 요청 (Payload)
```http
POST /api/auth/login HTTP/1.1
Content-Type: application/json

{
  "email": "sales.staff@baton.local",
  "password": "wrong_password_attack"
}
```

#### 3. 서버 실제 응답 (1~4회차 vs 5회차 비교)

**[1~4회차 응답 - 남은 횟수 감소]**
```http
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{
  "success": false,
  "data": null,
  "error": {
    "code": "AUTH_INVALID_CREDENTIALS",
    "message": "이메일 또는 비밀번호가 올바르지 않습니다.",
    "remainingAttempts": 1
  }
}
```

**[5회차 응답 - 계정 즉시 잠금]**
```http
HTTP/1.1 423 Locked
Content-Type: application/json

{
  "success": false,
  "data": null,
  "error": {
    "code": "AUTH_LOCKED",
    "message": "계정이 잠겼습니다. 15분 후 다시 시도해주세요.",
    "lockedUntil": "2026-11-10T10:00:15+09:00"
  }
}
```

#### 4. 서버 감사 로그 증적
```text
[AUDIT] LOGIN_FAILED email=s***@baton.local reason=BAD_CREDENTIALS attempts=4
[AUDIT] ACCOUNT_LOCKED email=s***@baton.local lockedUntil=2026-11-10T10:00:15+09:00
```

#### 5. 방어 분석 및 판정
- **결과**: **방어 성공 (PASS)**
- **원인 분석**: `AuthService` 및 `Member.recordLoginFailure()` 로직에 따라 5회 실패 즉시 `HTTP 423 Locked`로 전환되고, DB에 `locked_until`(+15분)이 기록됨. 이후 올바른 패스워드를 넣어도 잠금 만료 전까지 인증이 완전 차단됨.

### [점검 #3] OWASP A04 - 계정 열거(User Enumeration) 및 Timing Attack 점검

#### 1. 점검 개요
가입되지 않은 임의의 이메일을 무작위 전송하여 시스템에 등록된 계정 여부를 탐지하려는 계정 열거 공격을 시도함.

#### 2. 공격 요청 (Payload)
```http
POST /api/auth/login HTTP/1.1
Content-Type: application/json

{
  "email": "ghost.hacker@baton.local",
  "password": "anypassword123!"
}
```

#### 3. 서버 실제 응답
```http
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{
  "success": false,
  "data": null,
  "error": {
    "code": "AUTH_INVALID_CREDENTIALS",
    "message": "이메일 또는 비밀번호가 올바르지 않습니다.",
    "remainingAttempts": 4
  }
}
```

#### 4. 소요 시간 측정 (Timing Gap)
- **등록된 계정 비밀번호 불일치 소요 시간**: `78ms`
- **미등록 계정 로그인 시도 소요 시간**: `75ms`

#### 5. 방어 분석 및 판정
- **결과**: **방어 성공 (PASS)**
- **원인 분석**: 계정이 없더라도 "존재하지 않는 계정" 에러를 내지 않고, 실제 가입 계정의 첫 실패와 완전히 동일하게 `remainingAttempts: 4`를 반환함. 또한 `DUMMY_BCRYPT_HASH` 연산을 실행하여 응답 시간 차이를 3ms 이내로 상쇄함으로써 계정 존재 여부 판별을 무력화함.

### [점검 #4] OWASP A07 - JWT 서명 위변조(Signature Tampering) 점검

#### 1. 점검 개요
정상 발급된 사원의 Access Token에서 권한 상승(예: `jobRank: LEADER`)을 시도하거나 서명 값을 임의로 변조하여 보호된 엔드포인트에 요청함.

#### 2. 공격 요청 (Payload)
```http
GET /api/auth/me HTTP/1.1
Host: localhost:8080
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIzYWI1ZDc1Zi05MWU0LTRiOTUtOGU5YS0zNzA5M2ZhZjNiNzAiLCJpYXQiOjE3OTQyMTM5NTYsImV4cCI6MTc5NDIxNTc1Nn0.TAMPERED_INVALID_SIG_XYZ
```
* **입력값**: 서명(Signature) 문자열 끝자리를 임의의 영문자로 변조

#### 3. 서버 실제 응답
```http
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{
  "success": false,
  "data": null,
  "error": {
    "code": "AUTH_TOKEN_INVALID",
    "message": "유효하지 않은 토큰입니다."
  }
}
```

#### 4. 서버 감사 로그 증적
```text
[AUDIT] 인증 실패(401) - GET /api/auth/me from 127.0.0.1: JWT signature does not match locally computed signature
```

#### 5. 방어 분석 및 판정
- **결과**: **방어 성공 (PASS)**
- **원인 분석**: `JwtAuthenticationFilter` 및 `JwtProvider`에서 JJWT의 HMAC-SHA256 검증이 즉시 실패하여 `SecurityContext`에 인증 정보가 주입되지 않고 `401 Unauthorized`로 차단됨.

### [점검 #5] OWASP A07 - Refresh Token 재사용 탈취 공격(Replay Attack) 점검

#### 1. 점검 개요
정상 토큰 재발급 후 이미 폐기(Revoke)된 구버전 Refresh Token(`RT_1`)을 해커가 재사용하여 토큰 탈취를 시도하는 상황을 재현함.

#### 2. 공격 요청 (Payload)
```http
POST /api/auth/refresh HTTP/1.1
Host: localhost:8080
Cookie: baton_rt=already_revoked_old_refresh_token_string
```

#### 3. 서버 실제 응답
```http
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{
  "success": false,
  "data": null,
  "error": {
    "code": "AUTH_REFRESH_INVALID",
    "message": "유효하지 않은 리프레시 토큰입니다."
  }
}
```

#### 4. DB 상태 확인 증적
- **DB 쿼리 실행 확인**:
  ```sql
  UPDATE refresh_tokens SET revoked_at = NOW() WHERE member_id = 1;
  ```
- 공격 감지 즉시 해당 회원의 **모든 활성 Refresh Token이 강제 폐기** 처리됨.

#### 5. 방어 분석 및 판정
- **결과**: **방어 성공 (PASS)**
- **원인 분석**: Token Rotation 정책에 따라 이미 폐기된 토큰이 다시 인입되면 탈취 침해 사고로 간주하여, 피해 확산을 막기 위해 해당 회원의 모든 세션을 강제 만료 처리함.

### [점검 #6] OWASP A01 - IDOR 타인 대화 세션 무단 접근 점검

#### 1. 점검 개요
사원(김영업, memberId=1)의 토큰을 가지고 팀장(박영업, memberId=2)이 생성한 대화 세션(`sessionId=10`)의 메시지 이력을 무단 열람 시도함.

#### 2. 공격 요청 (Payload)
```http
GET /api/chat/sessions/10/messages HTTP/1.1
Host: localhost:8080
Authorization: Bearer <사원_Access_Token>
```

#### 3. 서버 실제 응답
```http
HTTP/1.1 404 Not Found
Content-Type: application/json

{
  "success": false,
  "data": null,
  "error": {
    "code": "SESSION_NOT_FOUND",
    "message": "대화 세션을 찾을 수 없습니다."
  }
}
```

#### 4. 서버 감사 로그 증적
```text
[AUDIT] SESSION_NOT_FOUND_OR_DENIED memberUuid=3ab5d75f-91e4-4b95-8e9a-37093faf3b70 sessionId=10
```

#### 5. 방어 분석 및 판정
- **결과**: **방어 성공 (PASS)**
- **원인 분석**: 세션 단건 조회 시 `WHERE id = :sessionId AND member_id = :myId`로 소유권을 함께 검증하여, 타인의 세션 번호가 존재하더라도 공격자에게는 `404 Not Found`로 은닉 처리되어 데이터 유출을 차단함.

### [점검 #8] OWASP A08 - 악성 실행 파일(EXE) 확장자 위조 업로드 점검

#### 1. 점검 개요
악성 윈도우 실행 파일(`exploit.exe`)의 확장자를 `exploit.pdf`로 변경하고 `Content-Type: application/pdf`로 위조하여 문서 업로드를 시도함.

#### 2. 공격 요청 (Payload)
```http
POST /api/documents HTTP/1.1
Host: localhost:8080
Authorization: Bearer <사원_Access_Token>
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary

------WebKitFormBoundary
Content-Disposition: form-data; name="file"; filename="exploit.pdf"
Content-Type: application/pdf

MZ......................(윈도우 PE 실행파일 매직넘버 4D 5A 바이너리 데이터)
------WebKitFormBoundary--
```

#### 3. 서버 실제 응답
```http
HTTP/1.1 400 Bad Request
Content-Type: application/json

{
  "success": false,
  "data": null,
  "error": {
    "code": "FILE_TYPE_NOT_SUPPORTED",
    "message": "지원하지 않는 파일 형식이거나 파일 내용이 손상되었습니다."
  }
}
```

#### 4. 방어 분석 및 판정
- **결과**: **방어 성공 (PASS)**
- **원인 분석**: 백엔드 `FileValidator`가 파일 확장자명에만 의존하지 않고, 파일의 첫 바이트(Magic Number)를 직접 검사하여 실제 PDF 시그니처(`%PDF-` / `25 50 44 46`)가 아닌 실행 파일 헤더(`MZ` / `4D 5A`)를 즉시 감지하여 차단함.
