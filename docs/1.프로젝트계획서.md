# 프로젝트 계획서

> 문서 상태: v0.3 (2026-11-07) · 산출물 1/9 · 작성: 황지영

## 1. 프로젝트 개요

### 1.1 프로젝트명
- **바톤 (Baton)** — 권한 필터 RAG 기반 사내 문서 AI 플랫폼
- 저장소: `baton-secure-handover`

### 1.2 프로젝트 목적
- **문제**: 부서별 업무 문서(매뉴얼, 절차서, 정책, 계약 현황 등)가 분류 없이 흩어져 있어 필요한 내용을 찾기 어렵고, 통째로 공유하면 직급·부서 권한 밖 정보(단가표, 성과평가 기준 등)까지 노출된다.
- **해결**: 문서를 올릴 때 **부서**와 **공개 직급**으로 분류해 문서함에서 관리하고, AI 업무 채팅은 **로그인한 사용자의 권한 범위 안의 문서함 내용만** 근거로 답한다. 권한 밖 문서는 Vector DB 검색 단계에서 제외되어 LLM에 전달되지 않는다.
- **3대 목적과의 연결**
  - ① LLM 연동: Backend → FastAPI(LangChain RAG) → SSE 스트리밍으로 화면까지 답변 전달
  - ② 안전한 백엔드: 권한 필터 자체가 서비스 핵심 → 인가·IDOR·LLM 정보 유출 점검이 기능과 직결
  - ③ 배포: 전 구성요소 Docker화 → GitHub Actions Build & Push → AWS EC2 Compose 배포
- **범위 원칙**: 핵심 도메인 1개(부서별 업무 문서 분류·관리) + AI 기능 1개(권한 필터 RAG 질의응답)
  - 제외: 회원가입 기능

### 1.4 사용자 및 권한 모델

**회원가입 없음** — 시연용 계정 4개를 Flyway 시드로 미리 등록한다.

| 계정 | 부서 | 직급 |
|------|------|------|
| 영업 사원 | 영업팀 (SALES) | 사원 (STAFF) |
| 영업 팀장 | 영업팀 (SALES) | 팀장 (LEADER) |
| 개발 사원 | 개발팀 (DEV) | 사원 (STAFF) |
| 개발 팀장 | 개발팀 (DEV) | 팀장 (LEADER) |

**문서 권한 = 부서 × 공개 직급**

- 부서: `SALES`(영업팀) / `DEV`(개발팀) / `ALL`(전체)
- 공개 직급: `STAFF`(사원 이상 열람) / `LEADER`(팀장만 열람)
- 열람 규칙: `(문서.부서 = ALL 또는 내 부서)` **AND** `(문서.공개직급 = STAFF 또는 내 직급 = LEADER)`

**시연용 예시 문서 10개 (권한 그룹 5개 × 2개)**

| # | 부서 | 공개 직급 | 예시 문서 |
|---|------|-----------|-----------|
| 1 | 전체 | 사원 | 사내 복리후생 안내, 비품 구매 절차 |
| 2 | 영업 | 사원 | 거래처 관리 매뉴얼, 월간 영업보고 작성법 |
| 3 | 영업 | 팀장 | 거래처 계약 단가표, 영업팀 성과평가 기준 |
| 4 | 개발 | 사원 | 개발 환경 세팅 가이드, 배포 절차서 |
| 5 | 개발 | 팀장 | 서버 접근권한 관리 정책, 외주 개발 계약 현황 |

> `전체 × 팀장` 조합은 시연 문서에서 사용하지 않는다(규칙상으로는 지원).

계정별 열람 가능 문서 수: 영업 사원 4 / 영업 팀장 6 / 개발 사원 4 / 개발 팀장 6

## 3. 기술 스택

- **Backend**: Java 17, Spring Boot 4.0.9, Spring Security 7.x, Spring Data JPA, WebClient, Bean Validation, Flyway
- **Frontend**: React 19.3.x + Vite, React Router, Zustand, Tailwind CSS, fetch 스트림(SSE 수신)
- **AI/ML**: Python 3.12, uv 0.12.23, FastAPI, LangChain(LCEL), Chroma
- **LLM·임베딩**: 개발 Groq + Ollama bge-m3 / 배포 OpenAI + text-embedding-3-small (LLM 모델명 미정, `7.AI모듈연동명세서.md` 3.1절)
- **Database**: MariaDB (`ddl-auto=validate` + Flyway), Chroma (권한 메타데이터 포함)
- **Security**: JWT, BCrypt, 로그인 잠금, CSP·CORS, 감사 로그 마스킹, Backend→AI 내부 API Key, Burp Suite, SBOM(CycloneDX), `npm audit`, gitleaks
- **Infrastructure**: Docker, Docker Compose, GitHub Actions(Build & Push → Docker Hub), AWS EC2 (선택: Minikube)

## 6. 성공 기준

- 로컬·EC2 모두에서 **로그인 → 문서 업로드 → 문서함 확인 → AI 질의응답(스트리밍·출처)** 이 동작한다
- 권한 테스트 질의 20개(계정 4개 × 권한 밖 문서 질문 5개)에서 **권한 밖 문서가 답변·출처에 나오는 경우 0건**
- 영업 사원 계정의 문서함에 팀장 전용·개발팀 문서가 **목록·검색·ID 직접 접근(상세·다운로드 API) 모두에서** 보이지 않는다
- 보안점검서에 취약점 3건 이상의 재현 → 조치 → 재확인 근거(전/후 코드, Burp 캡처, 로그)
- Git 이력·소스에 키/비밀번호 0건 (gitleaks 통과)
- GitHub Actions가 FE·BE·AI 이미지를 자동 빌드·Push
- 6명 모두 소유 디렉터리에 기능 커밋 + 보안 조치 커밋(`fix(security): ...`)이 있다

## 7. 협업 및 충돌 방지 규칙

- 디렉터리 소유권은 2장 표 기준, `CODEOWNERS`로 등록. 남의 디렉터리 변경은 소유자 승인 PR로만.
- 공용 파일 1인 소유: `infra/docker-compose.yml`·워크플로(F), `application.yml`(A), `build.gradle`(B), `package.json`(C), `pyproject.toml`·`uv.lock`(D), `.env.example`(F, 각 파트 추가 요청).
- 계약 우선: `4.API설계서.md`의 요청·응답·오류 형식과 Backend↔AI 내부 API를 Day 1에 동결. 변경은 설계서 PR 먼저.
- 병목 제거: C는 mock 응답으로 화면 선개발, B는 가짜 SSE로 중계 선테스트, D·E는 `retrieve(question, filter)` 시그니처만 합의 후 각자 구현.
- 브랜치: `main`(배포) / `develop`(통합) / `feature/<모듈>-<기능>`, 직접 푸시 금지, 1인 이상 리뷰 후 Create a merge commit.
- 커밋: `feat(ai): 권한 필터 retriever`, `fix(security): 타 부서 문서 조회 차단` — 보안 이슈 번호와 수정 커밋 연결.
- 매일 15분 스탠드업, 그날 끝낸 작업의 문서는 그날 작성.
