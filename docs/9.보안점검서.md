| F-1 | XSS | 입력창·채팅에 `<script>` / `<img onerror>` 입력 | 취약점 없음 | AI 답변은 `react-markdown`(v10) 기본 설정으로만 렌더링해 원시 HTML을 해석하지 않으며, `dangerouslySetInnerHTML`·`innerHTML`·`rehype-raw`는 사용하지 않음(코드 검색 0건). 사용자 메시지는 텍스트로만 표시 | ☑ (채팅에 `<img src=x onerror=alert(1)>` 입력 시 스크립트 실행 없이 글자 그대로 표시, 화면 캡처) |
| F-2 | (권장) 토큰 저장 위치 | localStorage / 메모리 / HttpOnly 쿠키 비교 | 취약점 없음 (설계 단계 방어 적용) | Access Token은 메모리(Zustand 스토어)에만 보관하고 Refresh Token은 HttpOnly 쿠키(B-6)로 처리. `localStorage`·`sessionStorage`·`document.cookie`를 사용하지 않아 XSS 발생 시에도 저장소 토큰 탈취 불가. 새로고침 시 `POST /api/auth/refresh`로 복구 | ☑ (로그인 상태에서 DevTools Local Storage 비어 있음 확인, 코드 검색 사용 0건) |

## 6. 취약점 조치 상세

### 6.1 비ASCII 내부 키 헤더로 500 응답 (AI 모듈)

- **관련 항목**: OWASP API2:2023 Broken Authentication, API8:2023 Security Misconfiguration / 점검서 A-1
- **재현 방법**:
    1. `/internal/*`에 `X-Internal-Api-Key` 헤더 값으로 한글 등 비ASCII 문자를 넣어 호출
    2. `hmac.compare_digest(문자열, 문자열)`이 비ASCII 문자열에서 `TypeError` 발생
- **영향**: 인증 실패가 401이 아닌 500으로 응답, 오류 모양도 FastAPI 기본값 `{"detail": ...}`라 명세서 오류 형식(`{"error":{"code","message"}}`)과 불일치. 서버 예외 발생으로 비정상 입력 처리 결함
- **조치 전** (`app/api/deps.py`): 헤더 값과 키를 **문자열끼리** `hmac.compare_digest`로 비교, 실패 시 FastAPI 기본 `HTTPException` 사용 → 비ASCII 값에서 `TypeError`(500), 인증 실패 응답은 `{"detail": ...}` 모양
- **조치 후 코드** (`app/api/deps.py`): 양쪽을 UTF-8 **바이트로 바꿔** 비교, 실패 시 `ApiError`로 명세서 오류 모양 응답
  ```python
  def verify_internal_key(x_internal_api_key: str | None = Header(default=None)) -> None:
      expected = get_settings().ai_internal_api_key.get_secret_value().encode("utf-8")
      given = (x_internal_api_key or "").encode("utf-8")
      # bytes끼리 비교: 헤더에 비ASCII 문자가 섞여도 TypeError(500) 없이 401로 끝난다
      if not given or not hmac.compare_digest(given, expected):
          raise ApiError(status.HTTP_401_UNAUTHORIZED, "INTERNAL_AUTH_FAILED", "내부 인증에 실패했습니다.")
  ```
- **재확인 결과**: 비ASCII 키 → 401 `INTERNAL_AUTH_FAILED`, 키 없음·틀린 키 → 401, 올바른 키 → 통과 (`test_internal_rejects_non_ascii_key_with_401_not_500`, `test_internal_rejects_missing_or_wrong_key`, `test_internal_accepts_right_key` 통과)

### 6.4 무차별 대입(Brute-Force) 공격 시 트랜잭션 롤백으로 계정 잠금 무력화 및 타임존 오차 (Backend)

- **관련 항목**: OWASP Web A07:2021 Identification and Authentication Failures / 점검서 B-5
- **재현 방법**:
    1. `POST /api/auth/login`에 동일 계정(`sales.staff@baton.local`)으로 잘못된 비밀번호를 5회 이상 연속 전송
    2. `LoginFailedException`·`AccountLockedException`(`RuntimeException` 상속) 발생 시 `@Transactional` 기본 롤백 정책으로 인해 `failed_login_count` 증가분이 DB에 커밋되지 않고 매번 `remainingAttempts: 4`로 초기화됨을 발견
    3. 또한 Docker 컨테이너(UTC) 환경에서 `LocalDateTime.now()`에 `.atZone(KST)`를 결합해 잠금 해제 시각(`lockedUntil`)이 9시간 과거로 계산되는 결함 발견
- **영향**: 공격자가 계정 잠금(423) 없이 무제한으로 비밀번호 무차별 대입(Brute-Force) 공격을 수행할 수 있음
- **조치 전 코드** (`backend/src/main/java/com/baton/auth/service/AuthService.java`):
  ```java
  @Transactional
  public LoginResult login(LoginRequest request) {
      ...
      LocalDateTime now = LocalDateTime.now();
      if (!passwordEncoder.matches(request.getPassword(), member.getPasswordHash())) {
          int remainingAttempts = member.recordLoginFailure(MAX_ATTEMPTS, LOCK_DURATION_MINUTES, now);
          // RuntimeException 발생 시 트랜잭션이 롤백되어 실패 횟수와 잠금 시각이 DB에 반영되지 않음
          throw new LoginFailedException(remainingAttempts);
      }
  ```
- **조치 후 코드** (`backend/src/main/java/com/baton/auth/service/AuthService.java`):
  ```java
  @Transactional(noRollbackFor = {LoginFailedException.class, AccountLockedException.class})
  public LoginResult login(LoginRequest request) {
      ...
      LocalDateTime now = LocalDateTime.now(KST);
      ...
      if (!passwordEncoder.matches(request.getPassword(), member.getPasswordHash())) {
          int remainingAttempts = member.recordLoginFailure(MAX_ATTEMPTS, LOCK_DURATION_MINUTES, now);
          memberRepository.save(member);

          if (remainingAttempts == 0) {
              OffsetDateTime lockedUntilKst = member.getLockedUntil().atZone(KST).toOffsetDateTime();
              log.warn("[AUDIT] ACCOUNT_LOCKED email={} lockedUntil={}", maskedEmail, lockedUntilKst);
              throw new AccountLockedException(lockedUntilKst);
          }

          log.warn("[AUDIT] LOGIN_FAILED email={} remainingAttempts={}", maskedEmail, remainingAttempts);
          throw new LoginFailedException(remainingAttempts);
      }
  ```
- **재확인 결과**: 1~4회 실패 시 `401 AUTH_INVALID_CREDENTIALS`(`remainingAttempts: 4 → 3 → 2 → 1`), 5회 실패 시 즉시 `423 AUTH_LOCKED` 및 KST 기준 `+15분` `lockedUntil` 반환, 잠금 중 올바른 비밀번호 입력 시에도 사전 차단 확인 (`bruteForceLockoutAfter5Failures`, `lockedAccountRejectsEvenCorrectPassword` 통과)

### 6.5 Refresh Token 탈취 재사용(Replay Attack) 감지 시 트랜잭션 롤백으로 일괄 폐기 취소 및 만료 시각 9시간 오차 (Backend)

- **관련 항목**: OWASP Web A07:2021 Identification and Authentication Failures / 점검서 B-4
- **재현 방법**:
    1. 정상 사용자가 `POST /api/auth/refresh`로 토큰을 회전(Rotation)하여 기존 Refresh Token이 폐기(`revoked_at` 기록)된 상태 생성
    2. 이미 폐기된 구 Refresh Token으로 다시 `/api/auth/refresh` 재발급 요청 전송
    3. `RefreshTokenService.validateAndRotate()`와 `AuthService.reissue()`가 기본 `@Transactional`로 선언되어 있어, `revokeAllByMemberId()` 호출 직후 던진 `BusinessException`(`RuntimeException`)에 의해 트랜잭션이 롤백되면서 일괄 폐기가 DB에 커밋되지 않는 결함 발견
    4. 또한 `AuthService`는 `LocalDateTime.now(KST)`로 만료 시각을 생성한 반면 `RefreshTokenService`는 컨테이너 기본값(`LocalDateTime.now()`, UTC)으로 비교하여 토큰 유효 기간이 7일이 아닌 7일 9시간으로 늘어나는 오차 발견
- **영향**: 탈취된 구 Refresh Token 재사용이 감지되어도 피해자·공격자의 다른 활성 세션이 실제로 폐기되지 않고 그대로 유지됨
- **조치 전 코드** (`backend/src/main/java/com/baton/auth/service/RefreshTokenService.java`, `AuthService.java`):
  ```java
  // RefreshTokenService.java
  @Transactional
  public Member validateAndRotate(String rawToken, String newRawToken, LocalDateTime newExpiresAt) {
      String tokenHash = hashToken(rawToken);
      LocalDateTime now = LocalDateTime.now(); // 컨테이너 UTC 기준 (KST와 9시간 오차)
      ...
      if (token.isRevoked()) {
          log.warn("[AUDIT] REFRESH_TOKEN_REUSE_DETECTED memberId={} tokenHash={}",
                  token.getMember().getId(), tokenHash);
          refreshTokenRepository.revokeAllByMemberId(token.getMember().getId(), now);
          // BusinessException(RuntimeException) 발생 시 @Transactional 기본 규칙으로 인해 위 일괄 폐기 쿼리가 함께 롤백됨
          throw new BusinessException(AuthErrorCode.AUTH_REFRESH_INVALID);
      }
  ```
- **조치 후 코드** (`backend/src/main/java/com/baton/auth/service/RefreshTokenService.java`, `AuthService.java`):
  ```java
  // AuthService.java
  @Transactional(noRollbackFor = {BusinessException.class})
  public LoginResult reissue(String rawRefreshToken) { ... }

  // RefreshTokenService.java
  private static final ZoneId KST = ZoneId.of("Asia/Seoul");

  @Transactional(noRollbackFor = BusinessException.class)
  public Member validateAndRotate(String rawToken, String newRawToken, LocalDateTime newExpiresAt) {
      String tokenHash = hashToken(rawToken);
      LocalDateTime now = LocalDateTime.now(KST);
      ...
      if (token.isRevoked()) {
          log.warn("[AUDIT] REFRESH_TOKEN_REUSE_DETECTED memberId={} tokenHash={}",
                  token.getMember().getId(), tokenHash);
          refreshTokenRepository.revokeAllByMemberId(token.getMember().getId(), now);
          refreshTokenRepository.flush();
          throw new BusinessException(AuthErrorCode.AUTH_REFRESH_INVALID);
      }
  ```
- **재확인 결과**: DB `refresh_tokens` 테이블에 원문 대신 64자 SHA-256 `token_hash`만 저장됨을 확인, 폐기 토큰 재사용 시 `401 AUTH_REFRESH_INVALID` 응답과 함께 롤백 없이 `revokeAllByMemberId` 및 `flush()`가 수행됨을 검증 (`reusedRevokedTokenTriggersFullRevocation` 통과)

### 6.6 비정상 JSON 본문 전송 시 예외 핸들러 누락으로 500 응답 반환 결함 (Backend)

- **관련 항목**: OWASP API8:2023 Security Misconfiguration / 점검서 B-8, B-11
- **재현 방법**:
    1. `curl.exe -i -X POST http://localhost/api/auth/login -H "Content-Type: application/json" -d "{broken_json}"` 실행
    2. 응답에 스택 트레이스는 노출되지 않았으나, 클라이언트 입력 오류임에도 `HTTP/1.1 500` (`INTERNAL_ERROR`) 반환 및 서버에 `[SYSTEM_ERROR]` 에러 로그 기록 확인
- **원인 및 영향**: `GlobalExceptionHandler`에 `@Valid` 검증 실패(`MethodArgumentNotValidException`)만 등록되어 있고, Jackson JSON 파싱 실패 시 발생하는 `HttpMessageNotReadableException` 핸들러가 누락되어 최상위 `Exception.class` 핸들러(500)로 빠짐. 잘못된 요청이 서버 장애(500)로 집계되어 모니터링을 오염시킴
- **조치 전 코드** (`backend/src/main/java/com/baton/common/GlobalExceptionHandler.java`):
  ```java
  // MethodArgumentNotValidException만 처리하고 HttpMessageNotReadableException 핸들러가 없어 Exception.class(500)로 이동
  @ExceptionHandler(Exception.class)
  public ResponseEntity<ApiResponse<Void>> handleException(Exception e) {
      log.error("[SYSTEM_ERROR] 처리되지 않은 예외 발생: {}", e.getMessage(), e);
      return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
              .body(ApiResponse.error(CommonErrorCode.INTERNAL_ERROR));
  }
  ```
- **조치 후 코드** (`backend/src/main/java/com/baton/common/GlobalExceptionHandler.java`):
  ```java
  @ExceptionHandler(HttpMessageNotReadableException.class)
  public ResponseEntity<ApiResponse<Void>> handleHttpMessageNotReadable(HttpMessageNotReadableException e) {
      log.warn("요청 본문 파싱 실패 (잘못된 JSON 형식): {}", e.getMessage());
      return ResponseEntity.status(HttpStatus.BAD_REQUEST)
              .body(ApiResponse.error(CommonErrorCode.VALIDATION_FAILED, "요청 본문 형식이 올바르지 않습니다."));
  }
  ```
- **재확인 결과**: 깨진 JSON 본문 요청 시 스택 트레이스 노출 없이 `400 Bad Request` (`{"success":false,"error":{"code":"VALIDATION_FAILED","message":"요청 본문 형식이 올바르지 않습니다."}}`) 반환 확인 (`GlobalExceptionHandlerTest.handleHttpMessageNotReadable` 통과)

### 6.7 클라이언트 입력 오류의 500 응답과 내부 클래스명 노출 (Backend)

- **관련 항목**: OWASP A02:2025 Security Misconfiguration, A10:2025 Mishandling of Exceptional Conditions / 점검서 B-11 (B-8과 연관)
- **재현 방법** (영업 사원 토큰, Burp Repeater):
    1. `POST /api/documents`에 `department=HR` → 400이지만 메시지가 `Failed to convert value of type 'java.lang.String' to required type 'com.baton.member.entity.Department' ...`
