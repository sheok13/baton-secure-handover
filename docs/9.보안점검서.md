## 6. 취약점 조치 상세

### 6.1 비ASCII 내부 키 헤더로 500 응답 (AI 모듈)

- **관련 항목**: OWASP API2:2023 Broken Authentication, API8:2023 Security Misconfiguration / 점검서 A-1
- **재현 방법**:
  1. `/internal/*`에 `X-Internal-Api-Key` 헤더 값으로 한글 등 비ASCII 문자를 넣어 호출
  2. `hmac.compare_digest(문자열, 문자열)`이 비ASCII 문자열에서 `TypeError` 발생
- **영향**: 인증 실패가 401이 아닌 500으로 응답, 오류 모양도 FastAPI 기본값 `{"detail": ...}`라 명세서 오류 형식(`{"error":{"code","message"}}`)과 불일치. 서버 예외 발생으로 비정상 입력 처리 결함
- **조치 전** (`app/api/deps.py`): 헤더 값과 키를 **문자열끼리** `hmac.compare_digest`로 비교, 실패 시 FastAPI 기본 `HTTPException` 사용 → 비ASCII 값에서 `TypeError`(500), 인증 실패 응답은 `{"detail": ...}` 모양
- **조치 후 코드** (`app/api/deps.py`): 양쪽을 UTF-8 **바이트로 바꿔** 비교, 실패 시 `ApiError`로 명세서 오류 모양 응답
  ```python
  def verify_internal_key(x_internal_api_key: str | None = Header(default=None)) -> None:
      expected = get_settings().ai_internal_api_key.get_secret_value().encode("utf-8")
      given = (x_internal_api_key or "").encode("utf-8")
      # bytes끼리 비교: 헤더에 비ASCII 문자가 섞여도 TypeError(500) 없이 401로 끝난다
      if not given or not hmac.compare_digest(given, expected):
          raise ApiError(status.HTTP_401_UNAUTHORIZED, "INTERNAL_AUTH_FAILED", "내부 인증에 실패했습니다.")
  ```
- **재확인 결과**: 비ASCII 키 → 401 `INTERNAL_AUTH_FAILED`, 키 없음·틀린 키 → 401, 올바른 키 → 통과 (`test_internal_rejects_non_ascii_key_with_401_not_500`, `test_internal_rejects_missing_or_wrong_key`, `test_internal_accepts_right_key` 통과)

### 6.4 무차별 대입(Brute-Force) 공격 시 트랜잭션 롤백으로 계정 잠금 무력화 및 타임존 오차 (Backend)

- **조치 후 코드** (`backend/src/main/java/com/baton/auth/service/AuthService.java`):

### 6.5 Refresh Token 탈취 재사용(Replay Attack) 감지 시 트랜잭션 롤백으로 일괄 폐기 취소 및 만료 시각 9시간 오차 (Backend)

- **관련 항목**: OWASP Web A07:2021 Identification and Authentication Failures / 점검서 B-4
- **재현 방법**:
  1. 정상 사용자가 `POST /api/auth/refresh`로 토큰을 회전(Rotation)하여 기존 Refresh Token이 폐기(`revoked_at` 기록)된 상태 생성
  2. 이미 폐기된 구 Refresh Token으로 다시 `/api/auth/refresh` 재발급 요청 전송
  3. `RefreshTokenService.validateAndRotate()`와 `AuthService.reissue()`가 기본 `@Transactional`로 선언되어 있어, `revokeAllByMemberId()` 호출 직후 던진 `BusinessException`(`RuntimeException`)에 의해 트랜잭션이 롤백되면서 일괄 폐기가 DB에 커밋되지 않는 결함 발견
  4. 또한 `AuthService`는 `LocalDateTime.now(KST)`로 만료 시각을 생성한 반면 `RefreshTokenService`는 컨테이너 기본값(`LocalDateTime.now()`, UTC)으로 비교하여 토큰 유효 기간이 7일이 아닌 7일 9시간으로 늘어나는 오차 발견
- **영향**: 탈취된 구 Refresh Token 재사용이 감지되어도 피해자·공격자의 다른 활성 세션이 실제로 폐기되지 않고 그대로 유지됨
- **조치 전 코드** (`backend/src/main/java/com/baton/auth/service/RefreshTokenService.java`, `AuthService.java`):
  ```java
  // RefreshTokenService.java

      String tokenHash = hashToken(rawToken);
      LocalDateTime now = LocalDateTime.now(); // 컨테이너 UTC 기준 (KST와 9시간 오차)
      ...
      if (token.isRevoked()) {
          log.warn("[AUDIT] REFRESH_TOKEN_REUSE_DETECTED memberId={} tokenHash={}",
                  token.getMember().getId(), tokenHash);
          refreshTokenRepository.revokeAllByMemberId(token.getMember().getId(), now);
          // BusinessException(RuntimeException) 발생 시 @Transactional 기본 규칙으로 인해 위 일괄 폐기 쿼리가 함께 롤백됨
          throw new BusinessException(AuthErrorCode.AUTH_REFRESH_INVALID);
      }
  ```
- **조치 후 코드** (`backend/src/main/java/com/baton/auth/service/RefreshTokenService.java`, `AuthService.java`):


### 6.9 컨테이너마다 필요 없는 비밀정보까지 전달 (인프라)

- **관련 항목**: OWASP A02:2025 Security Misconfiguration(최소 권한 위반) / 점검서 I-1
- **재현 방법** (로컬 Compose 기동 후, 값은 출력하지 않고 변수 이름만 확인):
  1. `docker exec baton-ai sh -c "env | cut -d= -f1 | sort"` → AI 모듈이 쓰지 않는 `JWT_SECRET_KEY`, `MARIADB_ROOT_PASSWORD`, `SPRING_DATASOURCE_PASSWORD`가 보임
  2. `docker exec baton-backend sh -c "env | cut -d= -f1 | sort"` → 백엔드가 쓰지 않는 `GROQ_API_KEY`, `OPENAI_API_KEY`, `MARIADB_ROOT_PASSWORD`가 보임
- **영향**: 컨테이너 하나가 침해되면 다른 구성요소의 비밀까지 함께 유출된다. 예를 들어 AI 모듈이 뚫리면 JWT 서명키로 임의 사용자 토큰을 위조하고, DB root 비밀번호로 전체 데이터에 접근할 수 있다.
- **원인**: `docker-compose.yml`의 `env_file: ../.env`가 루트 `.env` 전체를 백엔드·AI 컨테이너 환경변수로 넣음
- **조치 전 코드** (`infra/docker-compose.yml`):
  ```yaml
  ai-module:
    env_file: ../.env # .env 전체(DB root 비밀번호, JWT 서명키 포함)가 들어감
  backend:
    env_file: ../.env # LLM API 키까지 들어감
  ```
- **조치 후 코드**:
  ```yaml
  ai-module:
    # 최소 권한: AI 모듈이 읽는 변수만 주입. DB 비밀번호·JWT 서명키는 전달하지 않는다
    environment:
      AI_INTERNAL_API_KEY: ${AI_INTERNAL_API_KEY}
      LLM_PROVIDER: ${LLM_PROVIDER}
      LLM_MODEL: ${LLM_MODEL}
      GROQ_API_KEY: ${GROQ_API_KEY}
      OPENAI_API_KEY: ${OPENAI_API_KEY}
      EMBEDDING_PROVIDER: ${EMBEDDING_PROVIDER}
      EMBEDDING_MODEL: ${EMBEDDING_MODEL}
      OLLAMA_BASE_URL: ${OLLAMA_BASE_URL}
      VECTOR_STORE_PATH: ${VECTOR_STORE_PATH}
      CHROMA_COLLECTION: ${CHROMA_COLLECTION}
      RELEVANCE_THRESHOLD: ${RELEVANCE_THRESHOLD}
  backend:
    # 최소 권한: 백엔드가 읽는 변수만 주입. LLM API 키·DB root 비밀번호는 전달하지 않는다
    environment:
      SPRING_DATASOURCE_URL: jdbc:mariadb://database:3306/baton_db
      SPRING_DATASOURCE_USERNAME: ${MARIADB_USER}
      SPRING_DATASOURCE_PASSWORD: ${MARIADB_PASSWORD}
      JWT_SECRET_KEY: ${JWT_SECRET_KEY}
      AI_BASE_URL: http://ai-module:8000
      AI_INTERNAL_API_KEY: ${AI_INTERNAL_API_KEY}
      CORS_ALLOWED_ORIGINS: ${CORS_ALLOWED_ORIGINS}
      # (만료 시간·타임아웃·Actuator 노출 범위는 기본값과 함께 전달)
  ```
- **재확인 결과**: 같은 명령으로 AI 컨테이너에는 AI·LLM 관련 변수만, 백엔드 컨테이너에는 DB 접속·JWT·내부 API 키·CORS 변수만 남은 것 확인(`MARIADB_ROOT_PASSWORD`는 두 컨테이너 모두 없음). 전체 기동 후 로그인·문서함·채팅 정상 동작. EC2 배포 절차(`--env-file ../.env`)는 그대로이며 `.env`는 변수 치환에만 사용
- **증거**: [조치 전 AI](images/security/I-1/I-1-06_env-names-ai.png), [조치 전 백엔드](images/security/I-1/I-1-06_env-names-backend.png), [조치 후 AI](images/security/I-1/I-1-06R_env-names-ai-after.png), [조치 후 백엔드](images/security/I-1/I-1-06R_env-names-backend-after.png)

### 6.10 nginx 컨테이너 root 실행과 서버 버전 노출 (인프라)

- **관련 항목**: OWASP A02:2025 Security Misconfiguration / 점검서 I-2
- **재현 방법**:
  1. `docker top baton-frontend`, `docker top baton-nginx` → nginx 마스터 프로세스가 `root`로 실행
  2. `curl.exe -sI http://localhost/` → `Server: nginx/<버전>` 헤더로 정확한 버전 노출
- **영향**: nginx 취약점이 악용되면 공격자가 컨테이너 안에서 root 권한을 얻어 피해 범위가 커진다. 버전이 드러나면 해당 버전의 알려진 취약점을 골라 공격하기 쉬워진다.
- **원인**: 공식 `nginx:alpine` 이미지는 마스터 프로세스를 root로 실행하고, `server_tokens` 기본값이 `on`
- **조치 전 코드**:
  ```dockerfile
  # frontend/Dockerfile
  FROM nginx:alpine
  ```
  ```yaml
  # infra/docker-compose.yml
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx/local.conf:/etc/nginx/conf.d/default.conf
  ```
- **조치 후 코드**:
  ```dockerfile
  # frontend/Dockerfile — root 없이 동작하는 공식 nginx 이미지 (uid 101)
  FROM nginxinc/nginx-unprivileged:alpine
  COPY --from=build --chown=nginx:nginx /app/dist /usr/share/nginx/html
  ```
  ```yaml
  # infra/docker-compose.yml
  nginx:
    image: nginxinc/nginx-unprivileged:alpine
    ports:
      - "80:8080" # 일반 사용자는 80번을 직접 쓸 수 없어 컨테이너 8080으로 연결
    volumes:
      - ./nginx/local.conf:/etc/nginx/conf.d/default.conf:ro
  ```
  ```nginx
  # infra/nginx/local.conf, default.conf
  server {
      listen 8080;
      server_tokens off;      # 응답 헤더의 nginx 버전 숨김
  ```
- **재확인 결과**: 두 컨테이너 모두 `id` 결과 `uid=101(nginx)`, `docker top`에서 마스터·워커 프로세스가 root가 아닌 uid 101로 실행. 외부 접속 포트는 그대로 80(`0.0.0.0:80->8080`)이며 화면·SSE 채팅·업로드 정상 동작. `Server` 헤더 버전 숨김 〔확인: 캡처 추가〕
- **증거**: [조치 전](images/security/I-2/I-2-04_nginx-root.png), [조치 후](images/security/I-2/I-2-04R_nginx-nonroot.png)
