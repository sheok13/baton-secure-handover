# 컨테이너 배포 가이드

> 문서 상태: v0.4 (2026-11-10) · 산출물 8/9 · 작성: F 이승혁

## 1. 컨테이너 구성

바톤(Baton)은 컨테이너 4개(로컬은 Nginx 프록시 포함 5개)로 구성한다. Chroma는 별도 컨테이너 없이 AI Module 안에서 실행한다(`2.시스템아키텍처설계서.md` 1.1절).

- **Frontend**: React 19.3.x (Vite) + Nginx (정적 파일, `/api` 리버스 프록시)
- **Backend**: Spring Boot 4.0.9 + Java 17
- **AI Module**: Python 3.12 + uv 0.12.23 + FastAPI + LangChain, Chroma 내장(`PersistentClient`, 볼륨 `chroma_data`)
- **Database**: MariaDB 11.x
- **배포**: Docker Compose, GitHub Actions(Docker Hub), AWS EC2

## 2. Docker 설정 (Dockerfile)

모든 이미지는 비root 계정으로 실행하고, 멀티스테이지 빌드로 실행 이미지 크기를 줄인다. `.dockerignore`로 `.env`와 로컬 패키지가 이미지에 들어가지 않게 막는다.

### 2.1 Frontend Dockerfile (`frontend/Dockerfile`)

```dockerfile
# 1단계: 빌드 환경 (Node 20 LTS)
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# 2단계: 실행 환경 (Nginx)
# [참고] nginx.conf에는 /api 프록시(http://backend:8080), SSE용 proxy_buffering off와 읽기 타임아웃, CSP 등 보안 헤더를 둔다.
# [주의] nginx:alpine을 USER nginx로 실행하면 pid·캐시 경로 쓰기 권한 때문에 기동이 실패할 수 있다. 
# 실패할 경우 nginxinc/nginx-unprivileged 이미지(8080 포트)로 바꾸거나 해당 경로 권한을 조정한다.
FROM nginx:alpine
RUN chown -R nginx:nginx /usr/share/nginx/html && \
    chmod -R 755 /usr/share/nginx/html
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
USER nginx
EXPOSE 80
HEALTHCHECK --interval=30s --timeout=5s CMD curl -f http://localhost/ || exit 1
CMD ["nginx", "-g", "daemon off;"]
```

### 2.2 Backend Dockerfile (`backend/Dockerfile`)

```dockerfile
# 1단계: 빌드 환경 (Gradle + JDK)
FROM eclipse-temurin:17-jdk AS build
WORKDIR /app
COPY . .
RUN ./gradlew clean build -x test

# 2단계: 실행 환경 (JRE)
FROM eclipse-temurin:17-jre
WORKDIR /app
RUN useradd -m batonapp
COPY --from=build /app/build/libs/*.jar app.jar
RUN chown batonapp:batonapp app.jar
USER batonapp
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=5s CMD curl -f http://localhost:8080/actuator/health || exit 1
CMD ["java", "-jar", "app.jar"]
```

### 2.3 AI Module Dockerfile (`ai-module/Dockerfile`)

```dockerfile
# 1단계: 의존성 설치 (uv)
FROM python:3.12-slim AS build
COPY --from=ghcr.io/astral-sh/uv:0.12.23 /uv /uvx /bin/
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

# 2단계: 실행 환경 (.venv만 복사)
# [참고] slim 이미지에는 curl이 없으므로 HEALTHCHECK는 Python으로 한다(7.AI모듈연동명세서.md 11.2절).
# [참고] 내장 Chroma에 동시 쓰기가 생기지 않도록 워커는 1개로 둔다.
FROM python:3.12-slim
WORKDIR /app
RUN useradd -m aiapp && mkdir -p /data/chroma && chown aiapp:aiapp /data/chroma
COPY --from=build /app/.venv /app/.venv
COPY app ./app
RUN chown -R aiapp:aiapp /app
USER aiapp
ENV PATH="/app/.venv/bin:$PATH"
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=5s CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')" || exit 1
CMD ["uvicorn", "app.api.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "1"]
```

## 3. Docker Compose (`infra/docker-compose.yml`)

```yaml
# [네트워크] Frontend(80)만 호스트에 게시하고, 나머지 서비스는 ports 없이 내부 네트워크 baton-net에서만 통신한다.
# [실행 방법]
# - 로컬: docker compose up -d --build (이미지를 직접 빌드)
# - EC2: docker compose pull && docker compose up -d --no-build (Actions가 Push한 이미지 사용)
# [주의 사항] MariaDB와 chroma_data는 함께 초기화한다. 한쪽 볼륨만 지우면 문서함에는 보이는데 답변에 나오지 않는 불일치가 생긴다.
services:
  database:
    image: mariadb:11.2
    container_name: baton-db
    environment:
      MARIADB_ROOT_PASSWORD: ${MARIADB_ROOT_PASSWORD}
      MARIADB_DATABASE: baton_db
      MARIADB_USER: baton_app
      MARIADB_PASSWORD: ${MARIADB_PASSWORD}
    volumes:
      - db-data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"]
      interval: 10s
      timeout: 5s
      retries: 10
    restart: unless-stopped
    networks:
      - baton-net

  ai-module:
    build:
      context: ../ai-module
    image: ${DOCKERHUB_USERNAME}/baton-ai:${IMAGE_TAG:-latest}
    container_name: baton-ai
    env_file: ../.env
    expose:
      - "8000"
    volumes:
      - chroma_data:/data/chroma
    restart: unless-stopped
    networks:
      - baton-net

  backend:
    build:
      context: ../backend
    image: ${DOCKERHUB_USERNAME}/baton-backend:${IMAGE_TAG:-latest}
    container_name: baton-backend
    env_file: ../.env
    environment:
      SPRING_DATASOURCE_URL: jdbc:mariadb://database:3306/baton_db
      AI_BASE_URL: http://ai-module:8000
    expose:
      - "8080"
    depends_on:
      database:
        condition: service_healthy
      ai-module:
        condition: service_healthy
    restart: unless-stopped
    networks:
      - baton-net

  frontend:
    build:
      context: ../frontend
    image: ${DOCKERHUB_USERNAME}/baton-frontend:${IMAGE_TAG:-latest}
    container_name: baton-frontend
    ports:
      - "80:80"
    depends_on:
      backend:
        condition: service_healthy
    restart: unless-stopped
    networks:
      - baton-net

volumes:
  db-data:
  chroma_data:

networks:
  baton-net:
    driver: bridge
```

## 4. 환경 변수 및 비밀정보 관리

### 4.1 환경 변수 관리 원칙

- 실제 값이 든 `.env`는 `.gitignore`에 등록해 Git에 커밋하지 않는다.
- 저장소에는 값을 비운 `.env.example`만 커밋해 형식을 공유한다.
- CI/CD에 필요한 값은 GitHub Secrets에 등록하고, EC2에서는 서버에만 있는 `.env`를 쓴다.

### 4.2 주요 환경 변수 (`.env.example` 기준)

```env
# [인증·보안]
JWT_SECRET_KEY=                 # 32바이트 이상
AI_INTERNAL_API_KEY=            # Backend ↔ AI 내부 인증 헤더 값

# [Backend → DB·AI]
SPRING_DATASOURCE_URL=jdbc:mariadb://database:3306/baton_db
SPRING_DATASOURCE_USERNAME=baton_app
SPRING_DATASOURCE_PASSWORD=     # MARIADB_PASSWORD와 같은 값
AI_BASE_URL=http://ai-module:8000

# [MariaDB 컨테이너 초기화]
MARIADB_ROOT_PASSWORD=          # 앱에서 사용 금지
MARIADB_PASSWORD=

# [AI Module] 전체 목록은 7.AI모듈연동명세서.md 3.2절
LLM_PROVIDER=                   # groq | openai
LLM_MODEL=
EMBEDDING_PROVIDER=             # ollama | openai
EMBEDDING_MODEL=
VECTOR_STORE_PATH=              # /data/chroma/<임베딩 모델명>
GROQ_API_KEY=
OPENAI_API_KEY=

# [시드 스크립트]
SEED_PASSWORD=                  # upload_samples.sh 로그인용 시연 비밀번호

# [배포 이미지]
DOCKERHUB_USERNAME=
IMAGE_TAG=latest
```

## 5. 팀원 로컬 구동 및 테스트 가이드

각 파트(Frontend, Backend, AI) 개발 중이거나 통합 테스트를 진행할 때, 로컬 PC에서 컨테이너 환경을 직접 띄워볼 수 있다.

### 5.1 로컬 환경 구성 및 실행
1. **코드 최신화:** `git pull origin develop` 명령어로 최신 `docker-compose.yml` 및 코드를 받아온다.
2. **환경변수 세팅:** 프로젝트 루트의 `.env.example` 파일을 복사하여 `.env` 파일을 생성한다.
   - **필수 입력:** `.env` 파일 내 `DOCKERHUB_USERNAME` 란에 본인의 Docker Hub ID를 입력한다. (이미지 이름을 매핑하기 위함)
   - 기타 DB 비밀번호나 API 키 등은 팀 내 공유된 로컬 테스트용 값을 채워 넣는다.
3. **컨테이너 실행:** 터미널을 열고 프로젝트 폴더(`infra` 등 compose 파일 위치)에서 아래 명령어를 실행한다.
   ```bash
   docker compose up -d --build
   ```

### 5.2 로컬 정상 구동 검증
1. **컨테이너 상태 확인:** `docker ps` 명령어를 입력하여 컨테이너들이 모두 `Up (healthy)` 상태인지 확인한다.
2. **로그 확인:** 특정 컨테이너가 자꾸 종료된다면 `docker compose logs -f 컨테이너명`으로 에러 원인을 추적한다.
3. **접속 테스트:** 브라우저에서 `http://localhost` 에 접속하여 프론트엔드 화면이 정상 렌더링되고, 로그인 및 API 호출이 잘 동작하는지 점검한다.

## 6. 클라우드 배포 (AWS EC2)

- 보안 그룹: 인바운드는 80(HTTP)과 22(SSH, 팀 IP 한정)만 연다.

### 6.1 배포 절차
```bash
cd /home/ubuntu/baton-secure-handover
git pull origin develop
# .env는 EC2 안에서 직접 만든다 (Git에 없음)
cd infra
docker compose pull
docker compose up -d --no-build
```

### 6.2 배포 후 검증 절차
1. **도커 상태 확인:** 서버 터미널에서 `docker ps` 명령어로 전체 서비스가 `Up (healthy)` 상태인지 확인한다.
2. **서비스 접속 확인:** 팀 내 공유된 실서버 IP(`http://3.39.26.105` 등)로 접속하여 UI가 표시되는지 점검한다.
3. **API 연동 테스트:** 프론트엔드에서 로그인을 시도하거나 문서를 조회하여 Nginx의 `/api` 라우팅과 백엔드 연동이 정상 작동하는지 확인한다.
4. **시드 데이터 확인:** `upload_samples.sh` 스크립트를 통해 초기 시드 데이터가 문제없이 적재되었는지 검증한다.

## 7. CI/CD (GitHub Actions)

`main`, `develop` 브랜치에 병합(푸시)될 때마다 FE·BE·AI 이미지를 빌드해 Docker Hub에 자동 Push하는 파이프라인을 구축 완료했다.

- 워크플로 대상: Frontend, Backend, AI Module
- GitHub Secrets: `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`, 운영용 API 키

## 8. 네트워크 포트 및 보안 통제

모든 컨테이너는 내부 브리지 네트워크 `baton-net`으로 통신한다. Frontend 외에는 호스트(EC2) 밖으로 포트를 게시하지 않는다.

| 서비스 | 포트 | 외부 공개 | 통제 사유 및 접근 |
|--------|------|-----------|-------------------|
| Frontend | 80 | O | 사용자 브라우저 접속, `/api`를 Backend로 프록시 |
| Backend | 8080 | X | Nginx(Frontend) 프록시를 통해서만 접근 |
| AI Module | 8000 | X | Backend가 `X-Internal-Api-Key`를 붙여서만 호출 |
| Database | 3306 | X | Backend만 접근 (DB 직접 접근 차단) |
| Chroma | — | X | AI Module 컨테이너 안에서만 사용 (별도 포트 없음) |
