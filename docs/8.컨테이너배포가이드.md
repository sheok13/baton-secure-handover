# 컨테이너 배포 가이드

> 문서 상태: v0.8 (2026-11-12) · 산출물 8/9 · 작성: F 이승혁

## 1. 컨테이너 구성

바톤(Baton)은 앞단 리버스 프록시(`baton-nginx`)를 포함해 총 **5개 컨테이너**로 구성한다. Chroma는 별도 컨테이너 없이 AI Module 안에서 실행한다(`2.시스템아키텍처설계서.md` 1.1절).

- **Nginx (`baton-nginx`)**: 외부 80 포트 수신, `/`는 Frontend(3000)로, `/api` 및 SSE 스트리밍(`proxy_buffering off`)은 Backend(8080)로 리버스 프록시 (`infra/nginx/local.conf`)
- **Frontend (`baton-frontend`)**: React 19.3.x (Vite) + Nginx (내부 3000 포트에서 정적 파일 서빙 및 SPA `try_files` 처리)
- **Backend (`baton-backend`)**: Spring Boot 4.0.9 + Java 17 (Flyway DB 마이그레이션 내장)
- **AI Module (`baton-ai`)**: Python 3.12 + uv 0.12.23 + FastAPI + LangChain, Chroma 내장(`PersistentClient`, 볼륨 `chroma_data`)
- **Database (`baton-db`)**: MariaDB 11.2
- **배포**: Docker Compose, GitHub Actions(Docker Hub), AWS EC2, Kubernetes(K3s / Minikube 호환 표준 매니페스트)

## 2. Docker 설정 (Dockerfile)

멀티스테이지 빌드로 실행 이미지 크기를 줄이고, `.dockerignore`로 `.env`와 로컬 패키지가 이미지에 들어가지 않게 막는다. (Backend와 AI Module은 비root 계정으로 실행하며, Frontend Nginx는 포트·권한 충돌 방지를 위해 `USER nginx` 지시어를 제외하고 기본 데몬으로 구동한다.)

### 2.1 Frontend Dockerfile (`frontend/Dockerfile`)

```dockerfile
# 1단계: 빌드 환경 (Node 22)
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# 2단계: 실행 환경 (Nginx)
# [참고] 이 nginx.conf는 3000 포트에서 정적 파일과 SPA 새로고침 처리(try_files)만 한다.
# /api 프록시와 SSE 설정(proxy_buffering off 등)은 앞단 nginx 컨테이너(infra/nginx)가 맡는다.
FROM nginx:alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
RUN chown -R nginx:nginx /usr/share/nginx/html && \
    chmod -R 755 /usr/share/nginx/html

EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=5s CMD wget -qO- http://localhost:3000/ >/dev/null || exit 1
CMD ["nginx", "-g", "daemon off;"]
```

### 2.2 Backend Dockerfile (`backend/Dockerfile`)

```dockerfile
# 1단계: 빌드 환경 (Gradle + JDK)
FROM eclipse-temurin:17-jdk AS build
WORKDIR /app
COPY . .
RUN ./gradlew clean build -x test

# 2단계: 실행 환경 (JRE)
FROM eclipse-temurin:17-jre
WORKDIR /app
RUN useradd -m batonapp
COPY --from=build /app/build/libs/*.jar app.jar
RUN chown batonapp:batonapp app.jar
USER batonapp
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=5s CMD curl -f http://localhost:8080/actuator/health || exit 1
CMD ["java", "-jar", "app.jar"]
```

### 2.3 AI Module Dockerfile (`ai-module/Dockerfile`)

```dockerfile
# 1단계: 의존성 설치 (uv)
FROM python:3.12-slim AS build
COPY --from=ghcr.io/astral-sh/uv:0.12.23 /uv /uvx /bin/
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

# 2단계: 실행 환경 (.venv만 복사)
# [참고] slim 이미지에는 curl이 없으므로 HEALTHCHECK는 Python으로 한다(7.AI모듈연동명세서.md 11.2절).
# [참고] 내장 Chroma에 동시 쓰기가 생기지 않도록 워커는 1개로 둔다.
FROM python:3.12-slim
WORKDIR /app
RUN useradd -m aiapp && mkdir -p /data/chroma && chown aiapp:aiapp /data/chroma
COPY --from=build /app/.venv /app/.venv
COPY app ./app
RUN chown -R aiapp:aiapp /app
USER aiapp
ENV PATH="/app/.venv/bin:$PATH"
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=5s CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')" || exit 1
CMD ["uvicorn", "app.api.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "1"]
```

## 3. Docker Compose (`infra/docker-compose.yml`)

```yaml
# [네트워크] 앞단 nginx(baton-nginx)의 80 포트만 호스트에 게시("80:80")하고,
# frontend(3000), backend(8080), ai-module(8000), database(3306)는 호스트 게시 없이 내부 네트워크 baton-net에서만 통신한다.
# [실행 방법]
# - 로컬 및 최신 코드 직접 반영: docker compose --env-file ../.env up -d --build
# - EC2 (Docker Hub 이미지 배포): docker compose --env-file ../.env pull && docker compose --env-file ../.env up -d --no-build
# [주의 사항] MariaDB와 chroma_data는 함께 초기화(down -v)한다. 한쪽 볼륨만 지우면 문서함에는 보이는데 답변에 나오지 않는 불일치가 생긴다.
services:
  database:
    image: mariadb:11.2
    container_name: baton-db
    environment:
      MARIADB_ROOT_PASSWORD: ${MARIADB_ROOT_PASSWORD}
      MARIADB_DATABASE: baton_db
      MARIADB_USER: baton_app
      MARIADB_PASSWORD: ${MARIADB_PASSWORD}
    volumes:
      - db-data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"]
      interval: 10s
      timeout: 5s
      retries: 10
    restart: unless-stopped
    networks:
      - baton-net

  ai-module:
    build:
      context: ../ai-module
    image: ${DOCKERHUB_USERNAME}/baton-ai:${IMAGE_TAG:-latest}
    container_name: baton-ai
    env_file: ../.env
    expose:
      - "8000"
    volumes:
      - chroma_data:/data/chroma
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"]
      interval: 10s
      timeout: 5s
      retries: 3
    restart: unless-stopped
    networks:
      - baton-net

  backend:
    build:
      context: ../backend
    image: ${DOCKERHUB_USERNAME}/baton-backend:${IMAGE_TAG:-latest}
    container_name: baton-backend
    env_file: ../.env
    environment:
      SPRING_DATASOURCE_URL: jdbc:mariadb://database:3306/baton_db
      SPRING_DATASOURCE_USERNAME: ${MARIADB_USER}
      SPRING_DATASOURCE_PASSWORD: ${MARIADB_PASSWORD}
      AI_BASE_URL: http://ai-module:8000
    expose:
      - "8080"
    depends_on:
      database:
        condition: service_healthy
      ai-module:
        condition: service_healthy
    restart: unless-stopped
    networks:
      - baton-net

  frontend:
    build:
      context: ../frontend
    image: ${DOCKERHUB_USERNAME}/baton-frontend:${IMAGE_TAG:-latest}
    container_name: baton-frontend
    expose:
      - "3000"
    depends_on:
      backend:
        condition: service_healthy
    restart: unless-stopped
    networks:
      - baton-net

  nginx:
    image: nginx:alpine
    container_name: baton-nginx
    ports:
      - "80:80"
    volumes:
      - ./nginx/local.conf:/etc/nginx/conf.d/default.conf
    depends_on:
      - frontend
      - backend
    restart: always
    networks:
      - baton-net

volumes:
  db-data:
  chroma_data:

networks:
  baton-net:
    driver: bridge
```

## 4. 환경 변수 및 비밀정보 관리

### 4.1 환경 변수 관리 원칙

- 실제 값이 든 `.env`는 `.gitignore`에 등록해 Git에 커밋하지 않는다.
- 저장소에는 값을 비운 `.env.example`만 커밋해 형식을 공유한다.
- CI/CD에 필요한 값은 GitHub Secrets에 등록하고, EC2에서는 서버에만 있는 `.env` 및 Kubernetes `Secret`(`baton-env`)을 쓴다.

### 4.2 주요 환경 변수 (`.env.example` 기준)

```env
# [인증·보안]
JWT_SECRET_KEY=                  # 32바이트 이상
AI_INTERNAL_API_KEY=             # Backend ↔ AI 내부 인증 헤더 값

# [Backend → DB·AI]
SPRING_DATASOURCE_URL=jdbc:mariadb://database:3306/baton_db
SPRING_DATASOURCE_USERNAME=baton_app
SPRING_DATASOURCE_PASSWORD=      # MARIADB_PASSWORD와 같은 값
AI_BASE_URL=http://ai-module:8000

# [MariaDB 컨테이너 초기화]
MARIADB_ROOT_PASSWORD=           # 앱에서 사용 금지
MARIADB_PASSWORD=

# [AI Module] 전체 목록은 7.AI모듈연동명세서.md 3.2절
LLM_PROVIDER=                    # groq | openai
LLM_MODEL=
EMBEDDING_PROVIDER=              # ollama | openai
EMBEDDING_MODEL=
VECTOR_STORE_PATH=               # /data/chroma/<임베딩 모델명>
GROQ_API_KEY=
OPENAI_API_KEY=

# [시드 스크립트]
SEED_PASSWORD=                   # upload_samples.sh 로그인용 시연 비밀번호

# [배포 이미지]
DOCKERHUB_USERNAME=
IMAGE_TAG=latest
```

## 5. 팀원 로컬 구동 및 테스트 가이드

각 파트(Frontend, Backend, AI) 개발 중이거나 통합 테스트를 진행할 때, 로컬 PC에서 컨테이너 환경을 직접 띄워볼 수 있다.

### 5.1 로컬 환경 구성 및 실행
1. **코드 최신화:** `git checkout -f develop && git pull origin develop` 명령어로 최신 `docker-compose.yml` 및 코드를 받아온다.
2. **환경변수 세팅:** 전달받은 `.env` 파일을 프로젝트 루트에 배치하고 개인용 `GROQ_API_KEY`를 입력한다. (로컬 임베딩 사용 시 PC에서 `ollama pull bge-m3`를 1회 실행한다.)
3. **컨테이너 실행:** 터미널을 열고 `infra` 폴더에서 아래 명령어를 실행한다. (DB 스키마나 시드 변경 시 `down -v`로 볼륨 초기화 후 실행)
   ```bash
   cd infra
   docker compose --env-file ../.env up -d --build
   ```
4. **시드 문서 업로드:** 프로젝트 루트 폴더(Git Bash 등)에서 실행 권한 및 줄바꿈 정리 후 시드 업로드 스크립트를 실행한다.
   ```bash
   chmod +x ./infra/seed/upload_samples.sh
   sed -i 's/\r$//' ./infra/seed/upload_samples.sh
   SEED_PASSWORD='baton2026!' BASE_URL=http://localhost/api ./infra/seed/upload_samples.sh
   ```

### 5.2 로컬 정상 구동 검증
1. **컨테이너 상태 확인:** `docker compose --env-file ../.env ps` 명령어를 입력하여 5개 컨테이너(`baton-nginx`, `baton-frontend`, `baton-backend`, `baton-ai`, `baton-db`)가 모두 정상 기동(`Up` / `healthy`) 상태인지 확인한다.
2. **로그 확인:** 특정 컨테이너가 자꾸 종료된다면 `docker compose logs -f 컨테이너명`으로 에러 원인을 추적한다.
3. **접속 테스트:** 브라우저에서 `http://localhost` 에 접속하여 시드 계정(`sales.staff@baton.local`)으로 로그인 후 문서함 조회 및 채팅 질의응답이 잘 동작하는지 점검한다.

## 6. 클라우드 배포 (AWS EC2 - Docker Compose)

- 보안 그룹: 인바운드는 80(HTTP)과 22(SSH, 팀 IP 한정)만 연다.

### 6.1 배포 및 최신화 절차

#### A. CI/CD 이미지 Pull 방식 (일반 배포)
GitHub Actions가 `develop` 브랜치 푸시 후 Docker Hub 이미지 빌드를 완료했을 때 사용한다.
```bash
cd /home/ubuntu/baton-secure-handover
git fetch --all
git checkout -f develop
git reset --hard origin/develop

cd infra
docker compose --env-file ../.env pull
docker compose --env-file ../.env up -d --no-build
```

#### B. 클린 재빌드 및 DB 볼륨 초기화 방식 (스키마/마이그레이션 변경 또는 캐시 꼬임 발생 시)
이전 이미지 캐시가 남아 구버전이 뜨거나 Flyway 마이그레이션(`db/migration/*.sql`)을 처음부터 다시 태워야 할 때 사용한다.
```bash
cd /home/ubuntu/baton-secure-handover
git fetch --all
git checkout -f develop
git reset --hard origin/develop

cd infra
docker compose --env-file ../.env down -v --rmi all --remove-orphans
docker compose --env-file ../.env up -d --build --force-recreate

# 모든 컨테이너 Healthy 확인 후 시드 적재
cd /home/ubuntu/baton-secure-handover
chmod +x ./infra/seed/upload_samples.sh
sed -i 's/\r$//' ./infra/seed/upload_samples.sh
SEED_PASSWORD='baton2026!' BASE_URL=http://localhost/api ./infra/seed/upload_samples.sh
```

### 6.2 배포 후 검증 및 트러블슈팅 절차
1. **도커 상태 확인:** 서버 터미널에서 `docker compose --env-file ../.env ps` 명령어로 5개 서비스가 모두 `Up (healthy)` 상태인지 확인한다.
2. **서비스 접속 확인:** 팀 내 공유된 실서버 IP(`http://3.39.26.105`)로 접속하여 최신 UI가 표시되는지 점검한다.
3. **API 연동 및 DB 마이그레이션 점검:** 로그인 실패(`401`)나 테이블 누락 의심 시 아래 명령어로 Flyway 이력과 테이블 생성 여부를 검증한다.
   ```bash
   set -a && source ../.env && set +a
   docker exec -it baton-db mariadb -u root -p"$MARIADB_ROOT_PASSWORD" baton_db \
     -e "SELECT version, description, success FROM flyway_schema_history; SHOW TABLES;"
   ```
4. **시드 데이터 확인:** `upload_samples.sh` 스크립트를 통해 초기 시드 데이터 10건이 모두 `HTTP 201`로 적재되었는지 검증한다.

## 7. Kubernetes(K8s) 클러스터 아키텍처 및 배포 (`infra/k8s/`)

단일 YAML이 아닌 현업 표준에 맞춰 역할별로 분리된 **7종의 매니페스트 아키텍처(`00`~`06`)**를 설계하고, AWS EC2 상의 CNCF 공인 경량 쿠버네티스(K3s) 및 로컬 `Minikube` 클러스터에 배포 및 검증을 완료하였다. (모든 매니페스트는 표준 Kubernetes API를 준수하여 `K3s`, `Minikube`, 클라우드 `GKE` 환경에서 모두 동일하게 즉시 구동된다.)

### 7.1 매니페스트 파일 구조 (`infra/k8s/`)

| 파일명 | K8s 리소스 종류 | 주요 역할 및 설계 특징 |
|--------|-----------------|------------------------|
| `00-namespace.yaml` / `00-configmap.yaml` | `Namespace`, `ConfigMap` | `baton` 전용 격리 네임스페이스 생성 및 Nginx 리버스 프록시 라우팅(`nginx-config`) 정의 |
| `01-storage.yaml` | `PersistentVolumeClaim` | MariaDB(`db-data-pvc`, 5Gi) 및 ChromaDB(`chroma-data-pvc`, 10Gi) 영속 볼륨(RWO) 바인딩 |
| `02-database.yaml` | `Deployment`, `Service` | MariaDB 11.2 구동, UTF-8(`utf8mb4`) 설정, `Recreate` 전략 및 `securityContext(UID 999)` 적용, 내부 `ClusterIP`(3306) 노출 |
| `03-ai-module.yaml` | `Deployment`, `Service` | FastAPI + ChromaDB 구동, `/health` HTTP `readinessProbe` 적용, 내부 `ClusterIP`(8000) 노출 |
| `04-backend.yaml` | `Deployment`, `Service` | Spring Boot 구동, K8s 내부 DNS(`database:3306`, `ai-module:8000`) 연동, 내부 `ClusterIP`(8080) 노출 |
| `05-frontend.yaml` | `Deployment`, `Service` | React + Nginx 정적 서빙, 내부 `ClusterIP`(3000) 노출 |
| `06-nginx.yaml` | `Deployment`, `Service` | `ConfigMap`(`nginx-config`) 마운트, 외부 진입점인 **`LoadBalancer`(80 포트)** 단독 노출 |

### 7.2 Secret / ConfigMap 분리 및 배포 명령어 (K3s & Minikube 공통)

민감정보가 담긴 `.env`는 Git에 포함하지 않고 클러스터 내부 `Secret`(`baton-env`)으로 주입하며, 리버스 프록시 설정은 `ConfigMap`(`nginx-config`)으로 마운트한다.

```bash
# 1. 네임스페이스 우선 생성 및 전체 매니페스트(00~06) 배포
kubectl apply -f infra/k8s/00-namespace.yaml
kubectl apply -f infra/k8s/

# 2. .env 파일을 Secret(baton-env)으로 등록 (CRLF 및 값 뒤 공백 제거 보장)
kubectl create secret generic baton-env --from-env-file=.env -n baton --dry-run=client -o yaml | kubectl apply -f -

# 3. 파드 재시작 및 전 파드 Ready(1/1 Running) 상태 대기
kubectl rollout restart deployment -n baton
kubectl wait --for=condition=ready pod --all -n baton --timeout=120s
kubectl get all,pvc,configmap,secret -n baton

# 4. 초기 시드 문서 10건 적재 (Windows Git Bash 인코딩 깨짐 방지를 위해 Backend 컨테이너 내부에서 직접 실행)
BACKEND_POD=$(kubectl get pod -n baton -l app=backend -o jsonpath='{.items[0].metadata.name}')
MSYS_NO_PATHCONV=1 kubectl cp ./infra/seed baton/$BACKEND_POD:/tmp/seed
MSYS_NO_PATHCONV=1 kubectl exec -it $BACKEND_POD -n baton -- bash -c 'cd /tmp && mkdir -p infra && mv -f seed infra/ 2>/dev/null || true && chmod +x ./infra/seed/upload_samples.sh && SEED_PASSWORD="baton2026!" BASE_URL="http://localhost:8080/api" ./infra/seed/upload_samples.sh'

# 5. (Minikube 환경) 외부 브라우저 터널링 접속
minikube service nginx -n baton
```

### 7.3 Kubernetes 전환 및 Minikube 구동 과정의 핵심 트러블슈팅 사례

1. **MariaDB `RollingUpdate` 시 PVC/InnoDB 파일 락 충돌 해결**
   - **현상:** 매니페스트 수정 후 재배포 시 기존 DB 파드와 신규 DB 파드가 동시에 떠서 동일한 `db-data-pvc`(`ReadWriteOnce`) 볼륨을 마운트하며 InnoDB 파일 락(`ibdata1`) 충돌로 신규 파드가 `0/1 Running`에 멈춤.
   - **조치:** 단일 볼륨을 사용하는 Stateful 워크로드 특성에 맞춰 `02-database.yaml`의 배포 전략을 `strategy.type: Recreate`로 변경하여 기존 파드가 완전히 종료된 후 새 파드가 볼륨을 단독 마운트하도록 해결.
2. **Containerd 런타임의 `gosu mysql` 전환 멈춤(Hang) 및 `readinessProbe` 개선**
   - **현상:** K3s(`containerd`) 환경에서 MariaDB 컨테이너 기동 시 `Switching to dedicated user 'mysql'` 로그에서 멈추며 3306 포트가 열리지 않는 현상 발생(높은 파일 디스크립터 `ulimit` 환경에서 `gosu` 유저 전환 병목 및 볼륨 권한 이슈).
   - **조치:** 파드 스펙에 `securityContext` (`runAsUser: 999`, `runAsGroup: 999`, `fsGroup: 999`)를 명시하여 컨테이너가 처음부터 `mysql` 유저 권한으로 구동되도록 유저 전환 단계를 우회하고, `readinessProbe`를 `tcpSocket(port: 3306)`으로 구성하여 즉시 `1/1 Running` 상태를 확보함.
3. **Minikube 서비스 터널링 시 동적 포트 할당으로 인한 Spring Security CORS `403 Forbidden` 해결**
   - **현상:** 로컬 Minikube 환경에서 `minikube service nginx -n baton` 실행 시 외부 접속 주소가 `http://127.0.0.1:<랜덤포트>` 형태로 동적 할당됨. 기존 백엔드 `SecurityConfig.java`는 `setAllowedOrigins()`로 고정 포트(`http://localhost:5173`)만 허용하고 있어 로그인 및 API 요청 시 CORS `403` 에러 발생.
   - **조치:** `SecurityConfig.java`의 CORS 설정을 와일드카드 포트 매칭이 가능한 `setAllowedOriginPatterns()`로 전환하고, 기존 환경변수(`cors.allowed-origins`) 목록에 `http://localhost:*`, `http://127.0.0.1:*` 패턴을 추가하여 로컬·EC2·Minikube 전 환경 호환성을 확보함.
4. **K8s Secret(`baton-env`) 내 `OPENAI_API_KEY` 공백/개행 문자로 인한 AI 모듈 `502 Bad Gateway` 해결**
   - **현상:** 시드 문서 업로드 시 백엔드에서 `502 Bad Gateway`가 발생하고, `ai-module` 로그에 `openai.APIConnectionError: Connection error.`가 기록됨. 컨테이너 내부 네트워크는 정상(HTTP 421 응답 확인)이었으나, `.env`에서 주입된 `OPENAI_API_KEY` 값 끝에 포함된 공백(whitespace) 문자로 인해 Python `httpx`가 HTTP `Authorization` 헤더 생성 시 `Illegal header value` 프로토콜 에러를 발생시킴.
   - **조치:** `kubectl patch secret` 및 `echo -n ... | base64 -w 0`을 통해 공백과 개행이 완전히 제거된 API 키로 Secret을 패치하고 파드를 재기동하여 임베딩 생성 및 ChromaDB 적재를 정상화함.
5. **Windows Git Bash(MINGW64) 환경의 `curl` 멀티파트 한글 파일명 깨짐(CP949) 및 DB UTF-8 설정**
   - **현상:** Windows Git Bash에서 `upload_samples.sh` 실행 시 명령행 인자가 Windows 기본 인코딩(CP949)으로 변환되어 문서함 제목이 깨져서 적재됨.
   - **조치:** `02-database.yaml`에 `--character-set-server=utf8mb4` 설정을 추가하고, `kubectl cp`를 통해 시드 스크립트를 백엔드 파드(Linux `C.UTF-8` 환경) 내부로 복사해 직접 실행함으로써 호스트 OS 인코딩 및 포트포워딩 끊김 영향을 원천 차단함.

## 9. 네트워크 포트 및 보안 통제

모든 워크로드는 내부 브리지 네트워크(`baton-net`) 또는 쿠버네티스 내부 `ClusterIP`로만 통신한다. 앞단 리버스 프록시인 `nginx`(80) 외에는 호스트(EC2) 밖으로 포트를 게시하지 않는다.

| 서비스 | 컨테이너 / K8s 리소스 | 내부 포트 | 외부 공개 | 통제 사유 및 접근 |
|--------|-----------------------|-----------|-----------|-------------------|
| Nginx (Proxy) | `baton-nginx` (`LoadBalancer`) | 80 | O (`80:80`) | 사용자 브라우저 접속 수신, `/`는 Frontend(3000), `/api`는 Backend(8080)로 프록시 |
| Frontend | `baton-frontend` (`ClusterIP`) | 3000 | X | `nginx` 프록시를 통해서만 접근 (정적 파일 및 SPA `try_files` 처리) |
| Backend | `baton-backend` (`ClusterIP`) | 8080 | X | `nginx`의 `/api` 프록시를 통해서만 접근 |
| AI Module | `baton-ai` (`ClusterIP`) | 8000 | X | Backend가 `X-Internal-Api-Key`를 붙여서만 호출 |
| Database | `baton-db` (`ClusterIP`) | 3306 | X | Backend만 접근 (DB 직접 접근 차단) |
| Chroma | — (`chroma-data-pvc`) | — | X | AI Module 컨테이너 안에서만 사용 (별도 포트 없음) |
